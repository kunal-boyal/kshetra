| D29 | How sign-in works (module M1) | Every code request leaves a challenge, but only a registered number gets a code. An unknown number gets a decoy challenge whose code nobody receives, so both answer and verify the same way, count against the same rate limits, and take about as long; the code is sent without waiting for the provider. A person in several tenants gets a single-use, five-minute ticket after the code, and picks a tenant with it (`POST /auth/v1/select-tenant`); switching later spends the refresh token and ends the old tenant's session. Access tokens are ES256 JWTs that live 15 minutes, with the issuer and audience derived from `PRODUCT_SLUG` and a `cell` claim naming the deployment's `CELL_ID`; the JWKS is served at `GET /auth/v1/jwks`. Without `JWT_SIGNING_KEY` the API makes a temporary key at start-up, which production refuses. Refresh tokens are 32 random bytes kept as SHA-256 hashes; each use spends one, and a spent, expired or outdated one ends its whole family. Rate limits and tickets live in Redis under hashed keys. Device binding (D15) and the per-request user, device and revision checks move to step 5, which brings the users and devices tables they need. Spec 11.2 now lists the two new endpoints. | 2026-10-05, Kunal |
| D30 | How people and access work (spec 4.2, 5.3, M1 rules 5, 7 and 9, BR-38, BR-39) | **Who owns what.** The cell owns users, roles, designations and devices. The directory keeps a copy of each user's sign-in facts (phone, whether active, auth revision) in their membership. The cell sends that copy inside the transaction that changes it, as the user's whole state, and the directory ignores a state older than the one it holds. A membership belongs to one user for good; when the phone changes it moves to the new number's identity. Each number has at most one active membership per tenant, so `memberships` is unique on (tenant, user) and, among active rows, on (identity, tenant). **Signing in.** The directory asks the tenant's cell to admit each sign-in. The cell refuses an inactive user. It refuses a mobile-only role on the web with `USE_MOBILE_APP`. A phone must be the user's bound device, or becomes it when the user has none; otherwise the answer is `DEVICE_NOT_BOUND`. The bound device's ID stays with the refresh-token family and goes into the `did` claim. The app sends a random key it keeps in its secure store, and the cell stores only the key's SHA-256 (`devices.device_key_hash`). **Every request.** The cell checks that the tenant is open (otherwise `TENANT_SUSPENDED`), that the user is active at the token's revision, and that the token's device hasn't been reset (otherwise `SESSION_REVOKED`). It also checks that a web session belongs to a role allowed on the web. In phases 0 to 2 the cell reads tenant status from the directory module in process; once the directory runs separately, it will send status to the cells. The seams between the directory and the cell are in `apps/api/src/platform/planes.ts`, and `PlanesModule` wires them. **Routes.** Every route declares who may call it: `@Public()`, `@SignedIn()`, `@Requires(...)` or `@RequiresAny(...)`. A route that declares nothing is refused, and a test fails. **Scopes.** Every scope reaches the user's own records. `team` adds everyone below them in the reporting tree. `territory` adds everyone attached today at or below the territories they are attached to today. "Today" is in `Asia/Kolkata` until tenant settings give each tenant its own timezone. An attachment's `valid_to` is the first day it no longer applies. **Access rules.** Nobody gives access they don't hold: a role someone grants, creates or edits may contain only permissions they hold, and reach no further than their own scope does. Nobody changes their own role or status, edits the role they hold, or resets their own device. Someone who reaches less than the whole tenant adds or moves people only below someone they reach. A manager with active reports keeps their status, and keeps a designation that can have reports. The tenant admin role always holds every permission across the tenant. A change of phone, role or status, a device reset, or a sign-out from every device moves the auth revision. Creates, device resets and signing out everywhere take an `Idempotency-Key` header; PATCH is idempotent by itself. **Data.** Every cell table's primary key starts with `tenant_id`, and references between tables carry it too. Foreign-key checks bypass row-level security, but even so a row can't point into another tenant. Closure tables are derived from `manager_id` and `parent_id`, and moves rewrite them under a per-tenant advisory lock. Syncable tables (`users`, `territories`) take `row_version` from one sequence on insert and update. Roles carry `mobile_only`, and designations and territory levels carry their template key. Spec 10.3 and 11.2 now match. **Deferred.** These arrive later: the device-binding switch (on for everyone until tenant settings in step 6), custom user fields (with the config bundle), `calendar_id` (with calendars), dated transfers (M3), territory endpoints (M4), the device heartbeat and push token (phase 1), audit entries for resets and role changes (step 7), and what read-only mode still allows (M23). | 2026-10-06, Kunal |
| D31 | How configuration and text reach the apps (spec 5.1, 5.2, 8.4 to 8.6, 11.2, 11.3) | **The config bundle.** `GET /v1/config` holds the tenant's settings, its words resolved for each of its languages, its designations, and the caller's role, scope and permissions. Forms, account types, metrics and modules join it as their modules arrive. Its ETag is the config version plus the caller's role, so an app that already has the bundle gets a 304 with no body after one lookup. Every change to anything in the bundle moves `tenant_settings.config_version` on, whichever module made the change; today that covers settings, terminology, roles and designations. A separate `config-bundle` module assembles the bundle from the modules that own its parts, so none of them depends on another. Spec 12.7's Redis copy of the bundle waits until forms and metrics make it costly to build, since the ETag already spares most requests. **Settings.** The settings of spec 5.1 are a zod schema in `@kshetra/shared`, with their defaults in code. A tenant's row stores only what it changed, so a setting added later reaches every tenant with its default. Time zones are IANA names as written (`Asia/Kolkata`); offsets such as `+05:30` are refused, because databases and browsers read them differently. A brand colour must give white text a 4.5:1 contrast. English always stays among a tenant's languages, since missing text falls back to it. `PATCH /v1/settings` changes them. **Terminology.** A template's words become the tenant's overrides when the tenant is created. `GET` and `PUT /v1/terminology` read them and replace them as a whole. Plural messages pick their form by each language's rules; in Hindi, zero takes the singular. Hindi messages keep each term in a form that never changes, because a tenant's word can be either gender. | D32 | How changes are recorded and announced (module M21, spec 12.3, 12.4) | **Audit.** Every change writes an audit entry in the same transaction: the actor (a user, or the system while provisioning), the action, the target, the values before and after, and the request's address and device. Sign-ins and phones refused by device binding are recorded too; a refusal is written on its own, since nothing else commits. `audit_log` is partitioned by month in UTC, and a migration creates it, because Drizzle can't declare partitions. `cell.ensure_audit_log_partitions()` creates this month's partition and the next two, each with row-level security and append-only grants, since partitions inherit neither. The migration, the API at start-up and the relay every hour all call it. It runs as its owner, the migrator, and only `cell_app` may call it. The application can add and read entries but never change or remove them. `GET /v1/audit` (`audit.view`) pages from the newest entry, with filters; a role that reaches less than the whole tenant sees the entries of the people it reaches. **Outbox.** Events are written to `outbox_events` in the transaction of the change they report (spec 12.4) and delivered to their consumers as soon as that transaction commits. When a consumer fails, the relay retries the event with backoff, from 5 s doubling to 15 minutes. Delivery is at least once, so consumers are idempotent; each runs in a savepoint, inside the event's tenant. The relay finds due events across tenants through `cell.due_outbox_events()`, which returns only tenant and event IDs, and then delivers each one inside its tenant's row-level security. The same hourly upkeep purges delivered events after 3 days and idempotency keys after 7. Until the worker entrypoint arrives with the first BullMQ queue in phase 1, the API process runs the relay; `OUTBOX_RELAY=false` switches it off per process. The outbox table adds `attempts`, `next_attempt_at` and `last_error` to the columns of spec 10.3. **Directory sync.** This replaces part of D30. The directory's copy of a user's sign-in facts now follows the `user.created`, `user.updated` and `user.deactivated` events, instead of a call inside the cell's transaction. A user change no longer fails when the directory is briefly unreachable: the directory catches up when the event is delivered, while the cell refuses old tokens straight away. Until then, a new user can't sign in yet, and the cell refuses any token the directory refreshes for a deactivated user. | 2026-10-06, Kunal |

| D37 | The route registry, the cross-tenant contract test and the OpenAPI document (spec 11, 14.3, 14.4) | **Registry.** Every route declares its contract with `@Contract`: a summary, its group, and the zod schemas of its path parameters, query, body and answer, with whether it takes an `Idempotency-Key`. `routeRegistry()` in `apps/api/src/platform/routes.ts` reads every controller's decorators without starting the app: each route's method, path, success status, access rule and contract. A unit test fails for a route without an access rule or a contract, or with path parameters or an answer it doesn't describe. **Contract test.** `test/cross-tenant.int.test.ts` builds its cases from the registry and fails for any route without a fixture, as spec 14.4 asks. It sets up two tenants, A and B, each with people, a bound phone, their own role, designation, words and settings. Then, for every route, someone signed in to B tries A's IDs. Each ID must get exactly the answer an ID that exists nowhere gets: the same status and the same error, always a refusal (400, 403 or 404), so the answer doesn't even reveal that A's record exists. Reads must name nothing of A's. After every request, every row A owns, in every `cell` and `directory` table with a `tenant_id`, must be exactly as before.
