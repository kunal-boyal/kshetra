# Stage U6: Orders — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Orders look like the prototype's `WebOrders`: a register by month with status chips and their counts, beside a preview of the chosen order (lines, totals, its timeline), each order known by a short number ("Order 1187").

**Architecture:** Two API tasks (a per-tenant order number, then the register's summary and each order's history), then the register and the order page.

**Spec:** `docs/superpowers/plans/2026-10-27-ui-revamp.md` § Stage U6; the prototype's `WebOrders.dc.html`.

## Global constraints

- Money stays decimal strings through `@thelamp/shared`'s helpers; never `Number` for amounts on the server. The register's value is summed in SQL as `numeric`.
- The number is per tenant, from 1001, given in the placing transaction from a per-tenant counter row (`cell.order_counters`, locked by its upsert), so two phones never share one. Numbers are never reused and never change.
- Existing orders get numbers in the migration, in placing order. Phase U runs before launch, with no live tenant's orders, so the backfill is one statement rather than a job; the column is nullable until it is filled, then required.
- The history comes from the audit log (decision D32), read through the audit module's service, never its table.
- Nothing is lost: the status and date filters, the person and account filters the API takes, Load more, and the order page's decisions and fulfilment.
- The invoice match ("Matches invoice INV-2401") and "Import invoices" are out of scope (feature decision 4).

## Review focus

1. **Two orders placed at once.** They get different numbers. Tested in the API.
2. **A month with no orders.** The chips read 0, the meta "No orders", no preview. Tested.
3. **An order placed offline.** Its first step says so when it reached the server more than ten minutes after it was placed. Tested.
4. **A partly accepted, partly fulfilled order.** Its timeline lists each step once, in order. Tested.
5. **390 px.** The preview stacks under the register. Checked in the browser.

- [ ] Test (`test/orders.int.test.ts`): two orders get consecutive numbers from 1001; the number is in the order and the register.

### Task 2: the register's summary and the order's history

**Files:**
- `OrderListQuery` gains `period` (`YYYY-MM`, the tenant's clock; `from` and `to` win when given).
- `OrderListResult` gains `summary: { counts: Record<status, int>, orders: int, value: string } | null` with the first page only, under the filters but status.
- `OrderResult` gains `history: { kind: 'placed' | 'approved' | 'lines_decided' | 'rejected' | 'fulfilled' | 'partially_fulfilled' | 'cancelled', at, by: { id, name } | null, offline: boolean }[]`, from `AuditService.trail(tx, tenantId, 'order', id)`: each approver's decision at their step, as the audit log keeps them.
- [ ] Test: the summary counts by status and sums the value; a cursor page has none; the history of a decided and fulfilled order lists placed, accepted and fulfilled with their times.
