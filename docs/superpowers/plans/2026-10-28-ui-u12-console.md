# Stage U12: the console — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** The platform console reads as the prototype's `ConsoleTenants`, `ConsoleTenant`, `ConsoleOnboard`, `ConsoleBilling` and `ConsoleCells`: tenants with a strip of figures, seats and last activity; a tenant's page with its figures, a month of activity and its tools in a side card; a new tenant as numbered steps with what is chosen so far; plans as cards above invoices that say what happens next; and every cell's health in one table.

**Architecture:** One API task (the figures the console lacks), then one task a screen, then the comparison tool's console pairs.

**Spec:** `docs/superpowers/plans/2026-10-27-ui-revamp.md` § Stage U12; the prototype's `Console*.dc.html`.

## Global constraints

- Activity is what usage already counts (`UsageService`): a person is active on a day when one of their sessions was refreshed that day (`directory.refresh_tokens.created_at`), by membership, on the vendor's clock (`BILLING_TIME_ZONE`). A new index on `refresh_tokens (membership_id, created_at)` keeps these reads short.
- A tenant's seat limit is its entitlements' `limits.users` (`Entitlements.forTenant`), so licence mode and per-tenant limits count; null is no limit.
- Paying tenants have an active subscription and aren't demo; trial tenants have a trial that hasn't ended and no active subscription. Revenue waits for prices (decision D3) and isn't shown.
- An invoice's next step comes from `dunning()` in `@thelamp/shared` with the billing settings' periods, from the day after it fell due; the console never decides dunning on its own.
- A template's terms line is its own terminology in English and Hindi: the field user, the journey plan and the plan item.
- Nothing is lost: search and the status filter, suspending with a reason, termination, support grants, second-factor resets, the tenant's plan and billing cards, every step of a new tenant, the invoice filter and billing settings, and each cell's queues and hours.
- Out of scope (feature decision 4): phones waiting to sync per tenant (the cell's figure, not the tenant's), moving to a dedicated cell, the tenant's admins' names, monthly revenue, alarms and the safety-check card.

## Review focus

1. **A tenant nobody has used.** Last activity "Never", a month of empty bars, active today 0. Tested.
2. **A tenant without a seat limit.** Seats show the count alone; the summary's bought seats leave it out. Tested.
3. **An invoice paid, due, overdue in grace, read only and suspended.** Each says its next step. Tested.
4. **A cell that has not reported.** Its row says silent, with no figures. Tested.
5. **390 px.** Tiles stack, tables scroll in their boxes, the onboarding steps wrap. Checked in the browser.

### Task 1: the console's figures (API)

- `ConsoleTenant.seatLimit: int | null` and `lastActivityAt: datetime | null`.
- `GET /platform/v1/tenants/summary` → `ConsoleTenantSummary { tenants, paying, trial, demo, suspended, seatsInUse, seatsBought, activeToday }`.
- `GET /platform/v1/tenants/{id}/activity` → `ConsoleTenantActivity { days: [{ date, active }] (30, oldest first), activeToday, storageBytes: string | null }`.
- `TemplateSummary.terms: { en, hi }`; `InvoiceResult.plan: { key, name }`.
- Cross-tenant fixtures for the two routes (tenant tokens refused).
- [x] Tests (`test/console.int.test.ts`): the summary counts after a sign-in, a demo and a trial; a tenant's activity counts a refreshed session on its day; seat limit from the plan; a template's terms; an invoice's plan.

### Task 2: tenants

- Header with Onboard a tenant; `StatTile`s: paying (trial and demo under it), seats in use (of bought), active today (share of seats); the table: tenant, template, plan, seats (used / limit), cell as `<code>`, last activity, status.
- [x] Tests (`tenants.test.tsx`): the tiles; seats and last activity; "Never".

### Task 3: a tenant

- An initial-letter avatar, the name, "slug · template vN · customer since …", status and plan badges; tiles (seats, active today, last activity, storage); a card with 30 days of activity as bars (a list for screen readers) and a `DescriptionList` (cell, created, trial); a side card with support access, the tenant tools (export, suspend as a danger button, terminate). The plan, billing and second-factor cards stay.
- [x] Tests (`tenant.test.tsx`): the header, tiles and bars; Suspend asks in place.

### Task 4: a new tenant

- Six steps (company, template, first admin, brand, plan, review) shown as a numbered row; template choice as `ChoiceCard`s with each template's terms; a "So far" aside of what is filled. One form as now, its sections marking the steps.
- [x] Tests (`setup.test.tsx` or a new `new-tenant.test.tsx`): the template cards with terms; the summary follows the fields.

### Task 5: billing

- Plans as cards (name, tenants, price, modules) above invoices; invoices with plan and next step columns; the dunning notice from the settings' periods.
- [x] Tests (`billing.test.tsx`): the plan cards; next steps for paid, due, grace, read only and suspended.

### Task 6: health

- One table, a row per cell: cell, where, tenants, requests and errors in its last minute, jobs waiting, phones waiting, last report, status; the existing cards below as detail.
- [x] Tests (`health.test.tsx`): the table's rows and statuses, a silent cell.
